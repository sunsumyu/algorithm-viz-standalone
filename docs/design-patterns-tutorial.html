⚖️ 两适配器深化法则 (Two-Adapter Rule)

“一个适配器意味着假设的缝隙；两个适配器意味着真实的缝隙。除非跨缝隙有真正的变化，否则不要引入缝隙。” 当两个算法出现相似的拓扑绘制或状态演进时，必须在核心层抽象出真正的深模块。严禁单题内联手写 SVG 坐标或私造 stack 遍历。

📏 双重身材红线 (Dual LOC Guards)

策略身材红线：单题 *Strategy.ts LOC < 120 行（职责仅限入参提取、规约转换与委托调用）。

01. 策略模式 (Strategy Pattern)

别名 (Also known as)：政策模式 (Policy Pattern)

🎯 意图 (Intent)

定义一系列算法，把它们一个个封装起来，并且使它们可以相互替换。本模式使得算法可独立于使用它的客户而变化。

💡 解释 (Explanation)

🦄 通俗比喻 (Real-world Example)

在RPG游戏中，英雄屠龙时可随时根据龙的属性切换战术：面对喷火龙拔出大剑近战（MeleeStrategy），面对飞龙使用弓箭远程狙击（ProjectileStrategy），面对幽灵龙则咏唱圣光魔法（SpellStrategy）。英雄本身只发出一道「发动攻击」指令，具体的杀伤推演与动作逻辑全部委托给当前挂载的战术策略。在本项目中，面对 586+ 道算法（如不同路径、01背包、最长公共子序列），系统无需在渲染控制器中编写巨大的 switch-case，而是将每个算法的数学步进推演抽象为独立的策略类。

📖 通俗解释 (In Plain Words)： 策略模式允许在运行时根据上下文环境，动态挑选并切换最适用的算法实现，且算法的变更对调用者完全透明。
🏛️ 维基百科 / GoF 权威解释：

GoF《设计模式》定义：策略模式将可变的行为算法从核心业务环境中抽取为独立类型，通过持有策略接口的引用实现多态行为委托，消除硬编码条件分支。

import { IAlgorithmStrategy, StageExecutionParams } from './algorithm-strategy';
import { IYamlAlgorithmModel } from '../interfaces';
import { UniversalStep } from '../universal-stage-engine';
import { GridUniquePathsCompiler } from './grid-unique-paths-compiler';

export class GridUniquePathsStrategy implements IAlgorithmStrategy {
  public readonly modelId = 'unique-paths';

  public canHandle(modelId: string): boolean {
    return modelId === 'unique-paths' || modelId === 'unique-paths-ii';
  }

  public generateSteps(model: IYamlAlgorithmModel, params: StageExecutionParams): UniversalStep[] {
    const m = params.m ?? 3;
    const n = params.n ?? 7;
    const stage = params.stage ?? 3;

    // 根据演化阶段委托专属编译器进行数学填表推导
    switch (stage) {
      case 1:
        return GridUniquePathsCompiler.compileRecursion(m, n, params.direction);
      case 2:
        return GridUniquePathsCompiler.compileMemoization(m, n);
      case 3:
        return GridUniquePathsCompiler.compileTabulation(m, n, params.stageVariant);
      case 4:
        return GridUniquePathsCompiler.compileSpaceOptimized(m, n);
      default:
        return GridUniquePathsCompiler.compileTabulation(m, n);
    }
  }
}

集中管理所有注入的策略实例，提供根据 modelId 自动寻址与后备回退机制，彻底消除各模块手写 if-else 的恶疾。

📁 src/core/strategies/algorithm-strategy-registry.ts L9 ~ L74 
export class AlgorithmStrategyRegistry {
  private static strategies: IAlgorithmStrategy[] = [];

  public static register(strategy: IAlgorithmStrategy): void {
    const existingIndex = this.strategies.findIndex(s => s.modelId === strategy.modelId);
    if (existingIndex >= 0) {
      this.strategies[existingIndex] = strategy;
    } else {
      this.strategies.push(strategy);
    }
  }

  public static getStrategy(modelId: string): IAlgorithmStrategy | undefined {
    return this.strategies.find(s => s.canHandle(modelId));
  }

  public static clear(): void {
    this.strategies = [];
  }
}

export class UniversalStageEngine {
  public static executeModel(model: IYamlAlgorithmModel, params: StageExecutionParams): UniversalStep[] {
    // 1. 通过注册中心动态检索命中的推演策略 (Context 获取 Strategy)
    const strategy = AlgorithmStrategyRegistry.getStrategy(model.id);
    
    if (strategy) {
      // 2. 多态委派：策略独立演进推导步骤
      return strategy.generateSteps(model, params);
    }

    // 3. 后备通配降级机制 (Fallback)
    return UniversalStageEngine.executeFallbackMatrix(model, params);
  }
}

🛠️ 适用场景 (Applicability)

  • 当一个系统需要动态支持数十甚至数百种算法变体（如 580+ 道算法题的 DP、贪心、搜索推导）时；
  • 当代码中出现包含十几个分支的 switch (algoId) 或冗长 if-else 时；
  • 当算法的推导逻辑需要独立于视图层进行单元测试，要求输出纯净不可变数据时；
  • 当需要对算法作者施加「身材红线」约束（Strategy < 120行），隔离业务变更爆炸半径时。

⚖️ 优缺点权衡 (Consequences)

✅ 优点 (Pros)

  • 开闭原则 (OCP)：新增算法策略只需实现 IAlgorithmStrategy 并注册，无需改动核心引擎或既有算法；
  • 消除条件分支：彻底消灭庞大晦涩的 switch/case 分支代码；
  • 高内聚轻量化：每个策略专注自身数学规约，测试用例与实现紧密伴生；
  • 零 DOM 契约：返回纯内存数组，可在 Node.js/Vitest 下实现毫秒级高并发测试。

⚠️ 缺点 (Cons)

  • 策略类数量增加：每个算法或题族都会诞生对应的 Strategy 策略类；
  • 客户端需要感知：调用方必须知晓 modelId 与参数结构以匹配到对应的策略。
🛡️ 本项目深模块自愈消解方案： 本项目在架构层通过 AlgorithmStrategyRegistry 统一收口寻址，并由 AlgorithmCatalogIndexer 配合 AST 自动完成策略播种，完全规避了手写策略实例化的认知负担。

🔗 相关模式辨析 (Related Patterns)

策略模式 vs 状态模式： 策略模式强调算法的平行替换，通常由客户端外部决定注入哪种策略；状态模式侧重对象生命周期内部状态的自我转换，行为随内部状态流转自动改变。
策略模式 vs 模板方法： 策略模式使用对象组合（Composition），可以在运行时动态替换整套算法；模板方法使用类继承或固定算法骨架，在编译期固定骨架，子类仅重写具体步骤挂钩。
策略模式 vs 简单工厂： 简单工厂负责根据标识创建对象，返回的是对象实例；策略模式关注的是将算法行为封装并委托给持有引用的对象去执行。

02. 中介者模式 (Mediator Pattern)

别名 (Also known as)：调停者模式 (Intermediary Pattern)

🎯 意图 (Intent)

用一个中介对象来封装一系列的对象交互。中介者使各对象不需要显式地相互引用，从而使其耦合松散，而且可以独立地改变它们之间的交互。

💡 解释 (Explanation)

🦄 通俗比喻 (Real-world Example)

机场空中交通管制塔（Control Tower）：如果有 50 架飞机在机场上空准备降落，若让飞机与飞机之间互相通信协商高度与跑道，通信链路数量将高达 N*(N-1)/2 = 1225 条，极易导致灾难性混乱。空管塔作为中介者，所有飞机仅向空管塔报告位置，空管塔统筹调度后向各机发布航向与降落指令。在本项目中，可视化界面同时拥有【播放时间轴】、【Canvas/WebGL 画布】、【暗色代码终端】、【执行日志流】和【控制台按键】，组件间若直接相互调用会导致毁灭性的网状交叉依赖。VisualizerMediator 充当空管塔，原子化统一协调所有面板。

📖 通俗解释 (In Plain Words)： 中介者将组件间错综复杂的网状多对多关系，规约为以中介者为核心的星型一对多拓扑关系。
🏛️ 维基百科 / GoF 权威解释：

GoF《设计模式》定义：中介者模式定义一个集中的协调者对象，将一组同事对象（Colleagues）的通信完全解耦，使得对象间的交互行为可被集中控制和复用。

private handleStepTransition(stepIndex: number): void {
  this.state.currentStepIndex = stepIndex;
  const currentStep = this.state.steps[stepIndex];
  if (!currentStep) return;

  // 1. 协调同事 1: 更新 2D/3D 画布拓扑
  if (this.renderer) {
    this.renderer.updateStep(currentStep, { stage: this.state.stageNum });
  }

  // 2. 协调同事 2: 同步暗色终端代码高亮行号 (1-based)
  if (currentStep.codeLine !== undefined) {
    DarkCodeTerminalPresenter.highlightLine(currentStep.codeLine);
  }

  // 3. 协调同事 3: 更新 Card 4 执行日志流并触发自动平滑吸底
  ExecutionLogPresenter.renderStepLogs(
    document.getElementById('dsp-log-container')!,
    this.state.steps,
    stepIndex
  );

  // 4. 广播全局弱耦合领域事件
  eventHub.emit('step:change', {
    currentStep: stepIndex,
    totalSteps: this.state.steps.length,
    stepData: currentStep
  });
}

🛠️ 适用场景 (Applicability)

  • 一组对象以良好定义但高度复杂的方式通信，导致网状调用结构混乱时；
  • 一个组件由于引用了太多其他组件，导致自身无法被单独复用或单测时；
  • 想定制一个分布在多个类中的多步骤联动行为，而不希望生成大量子类时。

⚖️ 优缺点权衡 (Consequences)

✅ 优点 (Pros)

  • 降低参与者耦合度：将各同事组件间的网状 M*N 依赖降解为 1*N 简单星形依赖；
  • 集中控制流转逻辑：状态联动与时序调度逻辑收拢在单一中介者类中，查阅排错极为清晰；
  • 组件可独立单元测试：各同事组件无需知晓彼此存在，可单独进行 Mock 验证。

⚠️ 缺点 (Cons)

  • 中介者容易演化为上帝对象（God Object）：若不加节制，所有杂务都塞入中介者会导致其臃肿膨胀。
🛡️ 本项目深模块自愈消解方案： 本项目严格遵从 Matt Pocock 深模块身材红线，将纯数学推导剥离给 Strategy 编译器，将纯视图 DOM 渲染剥离给 Presenter/Adapter，中介者仅行使调度中转职责。

📁 src/core/controllers/visualizer-event-hub.ts L32 ~ L85 
export class VisualizerEventHub {
  private static instance: VisualizerEventHub | null = null;
  private listeners: Map<keyof VisualizerEventMap, Set<EventHandler<any>>> = new Map();

  public static getInstance(): VisualizerEventHub {
    if (!this.instance) {
      this.instance = new VisualizerEventHub();
    }
    return this.instance;
  }

  /**
   * 注册事件监听，返回无参注销闭包（RAII 资源自动释放）
   */
  public on<K extends keyof VisualizerEventMap>(
    event: K,
    handler: EventHandler<VisualizerEventMap[K]>
  ): UnsubscribeFn {
    if (!this.listeners.has(event)) {
      this.listeners.set(event, new Set());
    }
    this.listeners.get(event)!.add(handler);

    // 返回自清理闭包
    return () => this.off(event, handler);
  }

  /**
   * 广播事件：使用展开运算符进行防御式快照拷贝迭代
   */
  public emit<K extends keyof VisualizerEventMap>(
    event: K,
    payload: VisualizerEventMap[K]
  ): void {
    const handlers = this.listeners.get(event);
    if (!handlers || handlers.size === 0) return;

    // 防御性拷贝，防止 handler 内部调用 off 导致迭代死锁或跳项
    [...handlers].forEach((handler) => {
      try {
        handler(payload);
      } catch (err) {
        console.error(`[EventHub] Error in ${String(event)}:`, err);
      }
    });
  }

  public off<K extends keyof VisualizerEventMap>(event: K, handler: EventHandler<any>): void {
    this.listeners.get(event)?.delete(handler);
  }
}

export interface DfsHooks<TNode, TResult> {
  onEnterFrame?: (node: TNode, depth: number) => void;
  onBaseCaseCheck?: (node: TNode | null) => boolean;
  onLeafHit?: (node: TNode) => TResult;
  onBranchDive?: (parent: TNode, child: TNode, direction: 'left' | 'right') => void;
  onPostOrderReduce?: (node: TNode, leftResult: TResult, rightResult: TResult) => TResult;
}

export class BinaryTreeTraversalCompiler {
  /**
   * 模板方法：二叉树严格五段式 DFS 步进推导骨架
   */
  public static compileDfs<TNode = TreeNode, TResult = any>(
    root: TNode | null,
    hooks: DfsHooks<TNode, TResult>
  ): UniversalStep[] {
    const steps: UniversalStep[] = [];
    const callStack: TNode[] = [];

    // 核心算法骨架方法 (固定执行顺序，不可篡改)
    function dfs(current: TNode | null, parent: TNode | null, branch: string): TResult | null {
      // 1. 📥 步骤一：函数入口帧
      steps.push(createEnterStep(current, callStack));
      if (!current) {
        // 2. 🔍 步骤二：边界判空（自动注入父级 nullProbe 防断电探针）
        steps.push(createNullProbeStep(parent, branch));
        return null;
      }

      callStack.push(current);

      // 3. 🎯 步骤三：叶节点与特判挂钩
      if (isLeaf(current) && hooks.onLeafHit) {
        const leafRes = hooks.onLeafHit(current);
        steps.push(createLeafStep(current, leafRes));
      }

      // 4. 🔀 步骤四：深入左右分支子调用帧
      const leftRes = dfs(getLeft(current), current, 'left');
      const rightRes = dfs(getRight(current), current, 'right');

      // 5. 🔄 步骤五：后序归约与返回现场帧
      const finalRes = hooks.onPostOrderReduce
        ? hooks.onPostOrderReduce(current, leftRes, rightRes)
        : null;

      steps.push(createReturnStep(current, finalRes));
      callStack.pop();
      return finalRes;
    }

    dfs(root, null, 'root');
    return steps;
  }
}

export class PlaybackCoordinator {
  private status: PlaybackStatus = 'idle';
  private currentIndex: number = 0;
  private timer: number | null = null;
  private readonly options: PlaybackOptions;

  constructor(options: PlaybackOptions = {}) {
    this.options = options;
    this.currentIndex = options.initialIndex ?? 0;
  }

  /**
   * 状态迁移：触发播放
   */
  public play(): void {
    // 状态守卫：若当前已是 completed 状态，必须自动重置回第 0 步
    if (this.status === 'completed' || this.isFinished) {
      this.seek(0);
    }

    if (this.status === 'playing') return;

    this.status = 'playing';
    this.notifyStatusChange();
    this.scheduleNextTick();
  }

  /**
   * 状态迁移：暂停
   */
  public pause(): void {
    if (this.status !== 'playing') return;

    this.clearTimer();
    this.status = 'paused';
    this.notifyStatusChange();
  }

  /**
   * 单步前进时序守卫：状态感知行为
   */
  public stepForward(): boolean {
    // 如果处于播放中，单步触发强制降级为暂停
    if (this.status === 'playing') {
      this.pause();
    }

    if (this.currentIndex >= this.totalSteps - 1) {
      this.status = 'completed';
      this.notifyStatusChange();
      return false;
    }

    this.currentIndex++;
    this.notifyStepChange(false);
    return true;
  }

  private scheduleNextTick(): void {
    this.clearTimer();
    if (this.status !== 'playing') return;

    this.timer = window.setTimeout(() => {
      if (this.currentIndex < this.totalSteps - 1) {
        this.currentIndex++;
        this.notifyStepChange(true);
        this.scheduleNextTick();
      } else {
        // 自然播放至终局：自动迁移为 completed
        this.status = 'completed';
        this.clearTimer();
        this.notifyStatusChange();
      }
    }, this.speedMs);
  }
}

06. 管道与过滤器模式 (Pipes and Filters Pattern)

别名 (Also known as)：管道处理流水线 (Data Pipeline)

🎯 意图 (Intent)

将处理复杂数据流的系统分解为若干独立的子处理阶段（过滤器 Filter），各阶段通过标准管道（Pipe）串联，前一个过滤器的输出作为后一个过滤器的输入。

💡 解释 (Explanation)

🦄 通俗比喻 (Real-world Example)

📖 通俗解释 (In Plain Words)： 把一整套庞大的数据清洗与转换任务，拆解为一组依次执行、职责单一的过滤器流水线。

export class StepNormalizationEngine {
  /**
   * 管道总线入口：流水线串联执行四大防跳步自愈过滤器
   */
  public static normalize<T extends StepBase = StepBase>(
    rawSteps: T[],
    spec?: DeclarativeAlgorithmSpec<T>
  ): T[] {
    if (!rawSteps || rawSteps.length === 0) return [];

    // 管道组合串联：Filter1 ➔ Filter2 ➔ Filter3 ➔ Filter4
    const pipeline: StepFilter<T>[] = [
      this.filterZeroVisualBlackout,    // 过滤器 1: 画布防断电与动态探针锚点自愈
      this.filterCallReturnUnwind,      // 过滤器 2: 递归子调用返回现场帧缺失自愈
      this.filterGhostSteps,            // 过滤器 3: 连续无变化幽灵跳步剔除
      this.filterSequenceNumbering      // 过滤器 4: 1-based 序号与时间戳连续性校准
    ];

    return pipeline.reduce((currentSteps, filter) => filter(currentSteps, spec), rawSteps);
  }
}

private static filterZeroVisualBlackout<T extends StepBase>(
  steps: T[],
  spec?: DeclarativeAlgorithmSpec<T>
): T[] {
  let lastActiveTarget: HighlightTarget | null = null;

  return steps.map((step) => {
    const clone = { ...step };

    // 判定当前步骤是否为判空边界帧 (root == null)
    if (clone.codeLine === spec?.codeKeywords?.nullCheckLine) {
      if (!clone.highlights || clone.highlights.length === 0) {
        // 🚨 触发自愈：注入父节点探针锚点，动态渲染 ∅ null 虚线探针！
        clone.nullProbe = {
          parentVal: lastActiveTarget?.value ?? 'root',
          branch: lastActiveTarget?.branch ?? 'root'
        };
        clone.highlights = lastActiveTarget ? [lastActiveTarget] : [];
      }
    } else if (clone.highlights && clone.highlights.length > 0) {
      lastActiveTarget = clone.highlights[0];
    }

    return clone;
  });
}

检测递归退栈，若调用方返回现场帧缺失，自动合成平滑的「调用返回现场帧」，防止光标从子函数瞬间瞬移至下一物理语句。

private static filterCallReturnUnwind<T extends StepBase>(steps: T[]): T[] {
  const result: T[] = [];

  for (let i = 0; i < steps.length; i++) {
    const current = steps[i];
    const prev = steps[i - 1];

    // 检测到调用栈深度下降（退栈），且缺失调用方接收返回值的现场帧
    if (prev && prev.callStackDepth && current.callStackDepth && prev.callStackDepth > current.callStackDepth) {
      if (current.codeLine !== prev.callReturnLine) {
        // 自动插入合成的平滑返回帧
        const synthesizedReturnStep = {
          ...current,
          codeLine: prev.callReturnLine,
          log: `子调用执行完毕，控制权返回父层现场，恢复上下文...`
        };
        result.push(synthesizedReturnStep);
      }
    }

    result.push(current);
  }

  return result;
}

07. 适配器模式 (Adapter Pattern)

别名 (Also known as)：变压器模式 (Wrapper Pattern)

🎯 意图 (Intent)

将一个类的接口转换成客户希望的另外一个接口。适配器模式使得原本由于接口不兼容而不能一起工作的那些类可以一起工作。

💡 解释 (Explanation)

🦄 通俗比喻 (Real-world Example)

📖 通俗解释 (In Plain Words)： 在两个不兼容的接口之间搭建一座桥梁，让老组件或异构第三方组件无需修改即可接入新规范。

export class ThreeLayeredVoxelAdapter implements IVisualRenderer {
  public readonly id = 'three-layered-voxel';
  private engine!: NativeThreeVoxelEngine; // 持有被适配者引用 (Composition)

  public mount(container: HTMLElement): void {
    // 将底层 Three.js 画布注入到平台统一的容器中
    this.engine = new NativeThreeVoxelEngine(container);
  }

  public updateStep(step: UniversalStep, context?: VisualRendererContext): void {
    if (!this.engine) return;

    // 核心适配逻辑：将通用业务数据 UniversalStep 转换为 3D 体素空间状态
    if (step.gridState) {
      step.gridState.forEach((row, r) => {
        row.forEach((cellVal, c) => {
          const color = step.highlights?.some(h => h.r === r && h.c === c)
            ? 0x38bdf8  // 活跃高亮体素
            : 0x1e293b; // 常规底色体素
          this.engine.setVoxelColor(`${r}-${c}`, color);
        });
      });
    }

    this.engine.renderScene();
  }

  public dispose(): void {
    if (this.engine) {
      this.engine.dispose();
    }
  }
}

08. 桥接模式 (Bridge Pattern)

别名 (Also known as)：句柄/实体模式 (Handle/Body Pattern)

🎯 意图 (Intent)

将抽象部分与它的实现部分分离，使它们都可以独立地变化。

💡 解释 (Explanation)

🦄 通俗比喻 (Real-world Example)

通用遥控器与智能家电：如果设计 5 款不同品牌电视（索尼、三星、LG、小米、海信）且每款电视有 3 种遥控器（红外遥控、蓝牙遥控、手机App遥控），若采用紧耦合继承体系，需要写 5 * 3 = 15 个类。采用桥接模式，遥控器定义「抽象部分」（开机、关机、换台），电视定义「实现部分」（接收红外/蓝牙信号并驱动屏幕）。遥控器聚合电视接口，双方各新增 10 个型号只需 5+3=8 个类，彻底避免 M*N 类爆炸！在本项目中，【算法步进推演抽象】与【物理渲染呈现实现】彼此独立，一种 DP 矩阵可自由桥接 2D 表格或 3D 立体切片。

📖 通俗解释 (In Plain Words)： 用组合替代继承，把业务维度的变化和技术实现维度的变化彻底拆开，让两轴独立扩展。
🏛️ 维基百科 / GoF 权威解释：

GoF《设计模式》定义：桥接模式通过在抽象化与实现化之间建立一个关联桥梁，取代多层继承结构，实现两个独立变化维度的正交解耦。

09. 外观模式 (Facade Pattern)

别名 (Also known as)：门面模式 (門面模式)

🎯 意图 (Intent)

为子系统中的一组接口提供一个一致的界面，Facade模式定义了一个高层接口，这个接口使得这一子系统更加容易使用。

🦄 通俗比喻 (Real-world Example)

      </div>
    `;

  /**
   * 逐帧更新日志列表：高亮当前行、应用鲜蓝边框并平滑吸底滚动
   */
  public static renderStepLogs(
    container: HTMLElement,
    steps: StepLogEntry[],
    currentIndex: number,
    logCountEl?: HTMLElement | null
  ): void {
    if (!container) return;

    if (logCountEl) {
      logCountEl.textContent = `${currentIndex + 1} / ${steps.length} 步`;
    }

    // 渲染历史所有日志，当前步添加高亮标记
    container.innerHTML = steps.slice(0, currentIndex + 1).map((s, idx) => {
      const isCurrent = idx === currentIndex;
      const text = s.log || s.message || s.msg || s.decision || `步骤 ${idx + 1}`;
      const bgClass = isCurrent ? 'bg-blue-950/40 border-l-4 border-blue-500 text-blue-200' : 'text-slate-400 border-l-2 border-slate-700';

      return `<div class="p-1.5 pl-2 rounded transition-all ${bgClass}">
        <span class="text-slate-500 mr-2">#${idx + 1}</span>${text}
      </div>`;
    }).join('');

    // 自动平滑滚动吸底 (Auto Scroll to Bottom)
    container.scrollTop = container.scrollHeight;
  }
}

📁 src/core/algorithm-registry.ts L45 ~ L130 
export class AlgorithmRegistry {
  private static instance: AlgorithmRegistry | null = null;
  private metadataMap: Map<string, AlgorithmMetadata> = new Map();
  private manifests: Map<string, AlgorithmManifest> = new Map();

  public static getInstance(): AlgorithmRegistry {
    if (!this.instance) {
      this.instance = new AlgorithmRegistry();
    }
    return this.instance;
  }

  /**
   * 核心定位方法：一步解析算法清单（若未加载则自动按需触发动态分包 chunk 导入）
   */
  public async resolve(id: string): Promise<ResolvedAlgorithmEntry | null> {
    // 1. 若内存清单中已存在，直接返回
    if (this.manifests.has(id)) {
      return this.toResolvedEntry(this.manifests.get(id)!);
    }

    // 2. 查验元数据确认类目
    const meta = this.metadataMap.get(id);
    if (!meta) {
      console.warn(`[AlgorithmRegistry] Unknown algorithm ID: ${id}`);
      return null;
    }

    // 3. 惰性动态按需加载对应的 Webpack/Vite 分包 Chunk
    await loadAlgorithmBatch(meta.category);

    // 4. 加载完毕后再次从已注册清单中取出
    const loadedManifest = this.manifests.get(id);
    if (!loadedManifest) {
      throw new Error(`[AlgorithmRegistry] Failed to resolve manifest for ${id} after loading batch`);
    }

    return this.toResolvedEntry(loadedManifest);
  }

  public registerManifest(manifest: AlgorithmManifest): void {
    this.manifests.set(manifest.id, manifest);
  }
}

export class VisualRendererFactory {
  // 对象池缓存，复用长生命周期适配器
  private static renderers: Map<string, IVisualRenderer> = new Map();

  /**
   * 工厂方法：按类型构建或从对象池中提取渲染器实例
   */
  public static getRenderer(kind: RendererKind): IVisualRenderer {
    if (this.renderers.has(kind)) {
      return this.renderers.get(kind)!;
    }

    let renderer: IVisualRenderer;
    switch (kind) {
      case '3d-voxel':
        renderer = ThreeGridVisualAdapter.getInstance();
        break;
      case '2d-grid':
        renderer = new DOMGridVisualAdapter();
        break;
      case '3d-graph':
        renderer = new ThreeGraphTopologyAdapter();
        break;
      default:
        console.warn(`[VisualRendererFactory] Unknown kind: ${kind}, fallback to 2d-grid`);
        renderer = new DOMGridVisualAdapter();
        break;
    }

    this.renderers.set(kind, renderer);
    return renderer;
  }

  /**
   * 释放并清空所有工厂缓存实例
   */
  public static disposeAll(): void {
    this.renderers.forEach(r => r.dispose());
    this.renderers.clear();
  }
}

13. 建造者模式 (Builder Pattern)

别名 (Also known as)：生成器模式 (Builder)

🎯 意图 (Intent)

将一个复杂对象的构建与它的表示分离，使得同样的构建过程可以创建不同的表示。允许用户在不知道内部构建细节的情况下，通过流式调用一步步构建复杂实体。

💡 解释 (Explanation)

🦄 通俗比喻 (Real-world Example)

订制一台高性能台式组装电脑：如果你去买电脑，主板、CPU、显卡、散热水冷、DDR5内存、固态硬盘、电源机箱有几十种参数与安装次序（CPU要涂硅脂再压散热器，供电线要理线插防呆口）。如果把这 20 个参数直接作为构造函数入参：new PC(cpu, cooler, ram, ssd, gpu, psu, case, fan1, fan2, fan3...)，参数列表长达两米且极其容易把显卡和声卡位置传颠倒！建造者模式允许你使用流式装配器：builder.setCpu('i9').addRam(32).setGpu('RTX4090').build()，清晰可读且杜绝错漏。在本项目中，构造一个 3D 体素角色需要组装帽子、眼部、腮红、衣服、背包与四肢等 15+ 种材质与网格；构建一个 UniversalStep 需要组装网格、行号、日志、高亮、探针等 20+ 个状态字段。Builder 提供了极致优雅的构建体验！

📖 通俗解释 (In Plain Words)： 通过链式方法一步一步精细配置复杂对象的各个部件，最后调用 build() 一键输出完整对象。
🏛️ 维基百科 / GoF 权威解释：

GoF《设计模式》定义：建造者模式将一个复杂对象的构建过程抽取为一个独立的 Builder，通过分步执行构建方法并封装零件装配细节，使相同的构建流可产出不同配置的复杂对象。

14. 单例模式 (Singleton Pattern)

别名 (Also known as)：独生子模式 (Singleton)

🎯 意图 (Intent)

保证一个类仅有一个实例，并提供一个访问它的全局访问点。确保系统全局范围内某些核心资源管理者的唯一性与生命周期统一。

/**
 * 独占挂载：确保当前屏幕上永远只有一个活跃的可视化实例
 */
public mount(container: HTMLElement, renderer: IVisualRenderer): void {
  // 1. 互斥清理既有渲染器，防止 WebGL 上下文丢失或内存驻留
  if (this.currentRenderer) {
    this.currentRenderer.dispose();
    this.currentRenderer = null;
  }

  // 2. 清空既有容器 DOM 节点
  if (this.activeContainer && this.activeContainer !== container) {
    this.activeContainer.innerHTML = '';
  }

  this.activeContainer = container;
  this.currentRenderer = renderer;
  this.currentRenderer.mount(container);
}

public reset(): void {
  if (this.currentRenderer) {
    this.currentRenderer.dispose();
    this.currentRenderer = null;
  }
  if (this.activeContainer) {
    this.activeContainer.innerHTML = '';
    this.activeContainer = null;
  }
}

🛠️ 适用场景 (Applicability)

  • 当类只能有一个实例而且客户可以从一个众所周知的访问点访问它时；
  • 当这个唯一实例应该是通过子类化可扩展的，并且客户应该无需更改代码就能使用一个扩展的实例时；
  • 控制对系统排他性硬件或 DOM 资源的独占访问（如 WebGL 视口、音频引擎、事件总线）。

⚖️ 优缺点权衡 (Consequences)

✅ 优点 (Pros)

  • 受控访问：单例类封装它的唯一实例，可以严格地控制客户怎样以及何时访问它；
  • 缩小命名空间：单例模式是对全局变量的一种改进，它避免了那些存储唯一实例的全局变量污染系统命名空间；
  • 节约系统资源：避免昂贵对象（如事件总线、3D 渲染器上下文）的重复创建。

⚠️ 缺点 (Cons)

  • 单例模式容易隐藏依赖，降低代码的可测试性（单元测试之间容易产生状态污染）；
  • 在并发环境下需要考虑线程安全或时序竞争。
🛡️ 本项目深模块自愈消解方案： 本项目所有核心单例均配套严格的 reset() / clear() 生命周期钩子，在 Vitest beforeEach / afterEach 中统一清理，测试隔离度达到 100%。

🔗 相关模式辨析 (Related Patterns)

单例模式 vs 注册表模式： 注册表通常作为单例存在，单例是其实现手段，注册表是其承载元数据寻址的业务职责。
单例模式 vs 外观模式： 外观对象经常也是单例，因为只需要一个门面入口统一调度整个子系统。
