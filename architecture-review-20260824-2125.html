Problem: 4 个 HTML 文件各自内联 400+ 行几乎相同的协调逻辑（renderStep、loadAndInit、renderStageTabs、renderDirectionTabs、事件绑定、状态恢复），其中 Lite 与 Full 各两个文件互为字节级克隆。共计 ~1750 行重复代码散布在 4 份 HTML 内联脚本中。

Solution: 将协调逻辑提取为单一 VisualizerAppController 深模块，HTML 仅声明 DOM 骨架与一行 new VisualizerAppController({ mode: 'lite' | 'full', containerIds: {...} }).init()。

Wins

  • • leverage: 1 interface，4 call sites
  • • locality: 渲染/步进/切换 bugs 集中于一个模块
  • • interface 缩至 1 行初始化调用；implementation 吸收 ~1750 行重复
  • • 删除 2 个字节级克隆文件（stage-explorer 变为符号链接或 1 行 redirect）
  • • 可单元测试：注入 Mock DOM ids 即可覆盖协调流程

Problem: GridVisualAdapter 提取了 2D 网格渲染，但 Stage-4 的一维 memo 槽位着色（~35 行 isCur/isRef/val 判定 + DOM 生成）和 Stage-3 的状态转移看板（~20 行）仍留在 HTML 内联 renderStep 中，横跨模块 seam 泄漏。

Solution: 在 GridVisualAdapter 中新增 renderMemoSlots(container, step, n) 和 renderTransferEquation(container, step, direction)，将全部视觉渲染逻辑收编至同一深模块。

Wins

  • • locality: 所有「步骤数据 → DOM」转换集中于一处
  • • interface 不变宽（+2 methods），implementation 吸收 ~70 行
  • • renderStep 从 ~130 行缩减至 ~50 行纯协调逻辑

Problem: Lite 和 Full 各有独立的 HTML 骨架，但 stage-explorer 与 unique-paths 的骨架完全相同。若 Candidate 1 和 3 完成后，4 个 HTML 文件仍各自携带 200-280 行纯 DOM 模板。

Solution: 将 DOM 骨架提取为 2 个模板文件（lite-layout / full-layout），入口 HTML 仅做 <link> + <script> import + init()。这是 Candidate 1+3 的自然延伸，但需要先完成前两个。

Wins

  • • 入口文件从 800+ 行降至 ~5 行
  • • 新增 unique-paths-iii 或 edit-distance 可视化仅需 1 个新 URL 入口
  • • leverage: 2 个模板覆盖全部画板页面
⚠️ 依赖 Candidate 1 和 3 先完成。在此之前单独实施无净收益。

🏆 Top recommendation: Candidate 1

提取 VisualizerAppController 协调器深模块。这一步消除了 ~1750 行重复的内联脚本协调逻辑，是当前模板架构中最大的浅层摩擦来源。完成后 Candidate 2（渲染收编）和 Candidate 3（CSS 提取）成为自然的后续步骤，三者组合可将每个 HTML 入口从 800+ 行缩减到 ~200 行纯 DOM 声明 + 1 行初始化。
